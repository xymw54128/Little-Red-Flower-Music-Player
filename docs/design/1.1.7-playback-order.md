# Android 1.1.7 播放顺序审查与修复

2026-10-21。沿用 main，版本 1.1.7/code28。仅本地 Android，不推送 GitHub；保留 1.1.6 正式包及 code27 弹层修订包。

## 验收约定

音乐库、我喜欢和每个自建歌单独立保存歌曲名/歌手/随机/自定义排序。点歌时使用该来源最新的成员、标签和顺序，保留搜索/分组选择的子集；切到另一歌单并点击歌曲才更换队列，单纯浏览不更换。专辑仍按盘号/曲号，不受音乐库排序影响。队列为当前会话快照，不把搜索队列无条件补齐整个音乐库或歌单。

排序当前播放来源时以移动媒体项调整顺序，保持当前歌曲、进度和暂停/播放状态；排序其他歌单只更新对应歌单。随机播放使用实际遍历顺序展示队列；手动调整队列后退出随机遍历，使调整真正生效。普通循环/单曲模式保留原规则。

## 已确认问题

1. syncSourceOrder 在检查来源前取消共用 sortJob，快速先排活动 A 再排非活动 B 会取消 A 的同步。改为先校验当前来源。
2. 后来的手动队列编辑、下一首/队尾命令没有取消旧排序/批量移动任务，旧结果可能覆盖新操作。真正改变队列的入口统一取消这两类旧任务；对当前歌曲追加/下一首是既有无操作语义，直接返回而不取消有效排序。
3. 随机播放时 QueueSheet 把目标与物理队列比较：目标恰好等于物理列表时漏提交，未实际退出随机；原地结束拖动又可能错误退出随机。改为比较当前实际遍历。
4. 收藏页在等待新排序时保留旧行，立即点歌会把旧顺序传给播放器。点歌入口与排序同步共享 playbackSourceSongs，按最新来源重新选择/排序，过滤已删、非成员和不可用文件；失效点击不误播其他歌曲。仍保持 play 后直接 seek 的同步语义。
5. mode() 原来依赖滞后 UI 状态，快速多次点击可能重复同一模式；旧排序也可能关闭后来进入的随机模式。改读 controller 当前状态，用 modeRevision 标识后来的模式选择；排序仍完成，但不再关闭用户后来选择的随机模式。避免为了保留模式而丢掉已保存的排序。

## 具体改动与检查

PlaybackOrder.kt 放置共用纯顺序解析与实际遍历比较；MusicModel.kt 只改来源/队列/模式相关方法，不改解码或音效；PlayerUi.kt 改队列提交比较。PlaybackService.kt 保持原样。新增 JVM 顺序矩阵与真实 MusicModel 原生回归；更新原 smoke 用例按当前音乐库顺序检查上一首。

旧比较已用 QueueTraversalOrderTest 执行复现：3 项中 2 项失败，分别是“随机拖成物理顺序漏提交”和“原地拖动不应退出随机”。修复后全量结果记录至 dist/ANDROID-1.1.7-UI-CHECK.json。

设备未连接时仅确认 JVM 测试、构建、原生测试编译和代码审查，不宣称真实 MediaController/系统播放、下一首或手机帧率已实测。保留同签名与音频配置检查。
